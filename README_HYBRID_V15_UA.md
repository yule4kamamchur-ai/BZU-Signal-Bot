# BZU MULTI v15.0 HYBRID — встановлення та контроль

## Що змінилося

MEXC PAPER-сканер на семи активах тепер незалежний від важкого OKX v14.4.7. Шість сімейств аналізуються окремо на M1/M5 (LONG та SHORT), із трендовим контекстом M15/H1/H4, BTC, RVOL, структурним SL та оцінкою витрат. Розглядаються останні три M1, щоб не втрачати підтвердження між циклами. Старі oil-only детектори не перенесено дослівно: це адаптація їхніх концепцій до MEXC, а не заявлений фінансово доведений edge. Працюють ранні MARKET і рестинг LIMIT на придатному ретесті; LIMIT не є позицією до модельного виконання, TTL 8 хв. Залишено два PAPER-слоти.

Meta-оцінка: лише завершені попередні MEXC v15-угоди з придатною якістю даних, без старих OKX результатів і майбутніх міток; до 40 загальних і 12 локальних спостережень — COLLECTING_MEXC_LABELS. Потім лише обмежене коригування рангу, без блокування за ймовірністю; оцінка не калібрована незалежною історією. Оцінка 0–99 не є ймовірністю виграшу.

## Встановлення поверх чинного GitHub-репозиторію

1. Збережіть резервну копію актуального репозиторію, `multi_scanner_memory.json` та `multi_scanner_state.json`. Не замінюйте живі журнали файлами з повного архіву: вони з початкового зліпка (26.11.2026 19:38 Київ). Якщо є старі OKX DEMO/LIVE-позиції, перевірте, що їхній окремий runner залишається активним; не вимикайте супровід відкритих біржових позицій.
2. Застосуйте **BZU_HYBRID_v15_0_PATCH.zip** у корені репозиторію із заміною однойменних файлів і додаванням нових, включно з прихованою `.github/workflows/`. Патч НЕ містить JSON-станів/журналів. На Mac найнадійніше `unzip -o /шлях/до/BZU_HYBRID_v15_0_PATCH.zip -d /шлях/до/репозиторію`.
3. Перед оновленням зупиніть/дочекайтеся старих queued/in-progress MEXC запусків, щоб не було двох версій, які записують один журнал. Commit + push у default branch. У GitHub Settings → Actions → General дозвольте write permissions для Actions; Settings → Pages → Source: GitHub Actions. Запустіть Actions → BZU MULTI v15.0 — MEXC scanner → Run workflow.
4. GitHub резервно виконує скан `1-59/5 * * * *` (:01,:06,:11 тощо), окремо від старого OKX, з timeout 4 хв на scan job. Не встановлюйте cron */3 — мінімальний інтервал GitHub Actions 5 хвилин, можливі черги, а Pages deployment також може затримати показ. Офіційне джерело: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule
5. Для старого OKX PAPER окремо встановіть repository variable `BZU_RUN_LEGACY_OKX=true`, якщо він потрібен. Явні `BZU_OKX_EXECUTION=LIVE` або `DEMO` також зберігають незалежний legacy runner у GitHub-режимі; він має попередні налаштування й ключі. Старий OKX calibration запускається вручну або автоматично лише для активного legacy. Не запускайте двох writer-ів на одну пам'ять.

## Справжній 3-хвилинний цикл — Linux/VPS або постійно ввімкнений Docker

Це не GitHub Pages: браузер отримує актуальний атомарний JSON без деплою. Сервер не створено/не розгорнуто цим архівом. Потрібен Docker Compose v2 (для optional env_file — 2.24+), інтернет до MEXC.

1. Після завершення останнього GitHub scan встановіть repository variable `BZU_SERVER_MODE=WORKER` (зупиняє scheduled GitHub runner-и). Якщо старий OKX супроводжує реальні позиції, спочатку організуйте безперервний окремий супровід; WORKER зупиняє GitHub legacy runner теж.
2. На сервері в корені актуального репозиторію:

```bash
mkdir -p data
cp -n multi_scanner_memory.json multi_scanner_state.json data/
docker compose up -d --build
docker compose logs -f bzu-mexc-worker
```

Копіюйте найновішу пам'ять, не старий зліпок. Не перезаписуйте існуючий data/ при рестарті. Опційний `.env`: TELEGRAM_TOKEN, TELEGRAM_CHAT_ID, BZU_DEPOSIT_USDT, BZU_RISK_PCT, BZU_MAX_LEVERAGE, MEXC_TAKER_FEE_RATE, MEXC_SLIPPAGE_RATE. Не комітьте `.env`. MEXC API keys не потрібні. Worker цілить у новий старт кожні 180 секунд; якщо цикл затримався, не запускає паралельний writer. `http://127.0.0.1:8080/` на сервері; для віддаленого доступу потрібні SSH tunnel або ваш HTTPS reverse proxy. Не очікуйте, що стара адреса GitHub Pages автоматично стане адресою VPS.

Окремий старий OKX Docker доступний через `compose.legacy-okx.yaml`; у разі одночасного запуску треба окремі порти, state paths, і без дублювання його GitHub runner.

## Виправлення хронології

- `processed_until_ts` та `stop_effective_ts`: кожна закрита M1 обробляється один раз, SL після BE діє від кінця цієї свічки. Повтор свічок, рестарт, перенесений SL не створюють ретроспективний вихід.
- Після відкриття всередині M1 використовується тільки відома ціна її закриття та наступні повні M1, а також свіжі bid/ask. High/low неповної хвилини могли бути до входу; якщо могли торкнутись значущої межі — позначаємо `PARTIAL_ENTRY_BAR`, не вигадуємо порядок. Без історії tick/deals неможливо точно відновити рух усередині неповної хвилини. На пропусках — DATA_GAP. Стоп-first, коли в одному барі були обидві межі; такі записи не тренують meta. Геп через SL оцінюється за гіршою доступною ціною. Ліміти з неоднозначним fill не тренують meta. Немає справжніх біржових ордерів/гарантії заповнення.
- Міграція старої активної позиції: використовуємо останній курсор старого циклу, не перераховуємо старі свічки проти нового стопа; старий запис маркується LEGACY_CURSOR_MIGRATION. Старі daily stats архівуються, v15 daily починається окремо. Старі журнали не видаляються.
- Комісії та прослизання — **оцінка** (за замовчуванням 0.05% + 0.01% на кожний бік); funding не включено, реальні персональні тарифи потрібно задати. `net_r` v15 — модельний результат після цих оцінок, а не біржовий PnL. Два слоти поки зберігають стару per-slot політику sizing; сукупний margin/risk не обмежено одним депозитом. UI-калькулятор для нових сценаріїв не змінює серверні налаштування, активна угода відображає зафіксований sizing.

## Діагностика затримки

Архів: 19:38 Київ, не надано журнал запуску 19:46–20:00. Старий GitHub workflow мав 5 хв cron, запускав OKX перед MEXC, зберігав великі 84.9 MB journal / 32.8 MB memory і лише потім публікував Pages. Новий runner не чекає OKX, працює з малими MEXC файлами; REST OHLC запити — до 8 паралельних, timeout 7s на мережевий запит. Публічний JSON не містить довгих M1 серій. В дашборді вік аналізу, планова частота, тривалість скану, статус часткових/застарілих даних і WS цін. Повний збій API не підміняє час останнього успішного аналізу. Worker віддає JSON із Cache-Control:no-store. GitHub Pages все одно може затримувати публікацію, а завантаження браузера не є скануванням.

У Actions відкрийте запуск і перевірте `Queued`, `Validate and scan MEXC only`, `Persist small MEXC state only`, `Publish dashboard`. У логах `[MULTI-SCANNER]` видно `fresh=`, `timings`, `errors`. Для точної причини старої затримки потрібен run log або доступ до GitHub.
