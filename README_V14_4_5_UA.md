# BZU v14.4.5 — оновлення поверх v14.4.4

## Встановлення

1. Зробіть резервну копію репозиторію та зупиніть запуски на час заміни. Розпакуйте архів у корінь репозиторію, зберігаючи шляхи (включно з прихованою папкою `.github/workflows`). Замініть однойменні файли та додайте нові одним комітом. Це патч, а не повний репозиторій.
2. **Не видаляйте та не перезаписуйте** `last_signal_v6_4.json`, `signal_journal_v6_4.json`, `market_history_v12.json`, `research_market_v12_6.json`, `meta_priors.json`, `.env` або секрети. Вони не входять до патча. Збережені позиції та старі мітки не перекваліфіковуються автоматично. Старий апріор може застосовуватися як `LEGACY_BAYES_TRANSFER`, якщо він сумісний.
3. Для першої перевірки використовуйте `BZU_OKX_EXECUTION=PAPER` та `BZU_ADAPTIVE_EXITS=SHADOW`. Не перемикайтеся в LIVE за результатом цього короткого тесту. Переконайтеся, що версія на дашборді `full-ict-v14.4.5-intraday`, а статус нової моделі відповідає реальному стану калібрації.

## Що змінено

- Збережено всі 24 детектори та структурні захисні правила. Низька прогнозна ймовірність сама по собі більше не вимагає підтвердження входу. Виправлено передачу `source_strategy` у фінальний розрахунок ризику та узгоджено підтверджений MARKET / LIMIT body retest.
- Нова модель `expectancy_model.py`: P(win), P(fill), середні виграш/збиток після модельованих витрат, очікування на виконану угоду та на спробу входу; ієрархічне згладжування малих вибірок. Враховуються 11 контекстних полів. EV впливає на ранжування і ризик тільки після валідованого сумісного апріору. Модель не має окремого veto входу. Структурні ліміти ризику залишено.
- Тіньові сценарії нової схеми використовують основний lifecycle, незалежно від зайнятості портфеля. Дедуплікація за подією та геометрією входу, відділення не заповнених і неоднозначних сценаріїв від фактичних модельованих результатів, відсікання майбутніх міток. Старі мітки не використовуються для навчання v2. Незалежність епізодів наближено оцінюється за неперекриттям інтервалів.
- Режимні профілі MFE/Ratchet (TREND/RANGE/COUNTER) доступні експериментально. За замовчуванням SHADOW: нові пороги не застосовуються, чинні правила виходу лишаються. Це не незалежно доведений новий ATR-трейлінг.
- Опційний публічний OKX WebSocket ticker у безперервному worker, перевірка свіжості та коректності bid/ask, REST fallback. Новий транспорт не виконує приватних ордерів. Реальне проковзування, funding і біржовий PnL не звірялися; історичне виконання моделюється.
- Дашборд розрізняє legacy Bayes і expectancy v2. Додано щотижневий workflow калібрації, ручний запуск і контроль сумісності перед публікацією.

## Калібрація

У GitHub Actions виберіть **BZU Meta Calibration v14.4.5** -> **Run workflow**. `days=180`, `scan_minutes=5` для GitHub або `3` для worker; `adaptive_exits=SHADOW`. Для першого запуску `publish=false` (звіт і мітки в артефакті). Для публікації після перевірки — `publish=true`. Щотижневий workflow намагається опублікувати тільки валідований сумісний апріор, якщо код стратегії не змінився за час навчання. За недостатніх даних попередній файл зберігається.

Новий апріор вимагає не менше 20 незалежних заповнених перевірочних епізодів у щонайменше двох часових вікнах; поліпшення Brier score, MAE очікування та результату порівняно зі сталим множником ризику 0.65. Це критерії мінімальної перевірки, не гарантія прибутковості. Не підміняйте `meta_priors.json` невалідованим звітом. `EMPIRICAL_EXPECTANCY_V2` означає, що модель пройшла ці критерії та підпис відповідає коду/конфігурації. Інакше нова оцінка залишається моніторингом, а поточний fallback продовжує працювати.

## Worker (необов'язковий, окрема міграція)

GitHub-only режим залишається працездатним. Якщо є VPS: встановіть Docker, скопіюйте поточний стан та журнали у `./data/`, налаштуйте `.env` і PAPER. Перед запуском worker встановіть у GitHub `BZU_SERVER_MODE=WORKER` і переконайтеся, що старий workflow завершився. Запускайте лише один executor. `docker compose up -d --build`. Worker намагається виконувати цикл кожні 3 секунди, аналіз має конфігурацію 3 хвилини; фактична затримка залежить від API і часу обчислення. `BZU_PUBLIC_WS=true` використовує публічний ticker із REST fallback. Після публікації нового апріору синхронізуйте файл з GitHub і перебудуйте контейнер (або змонтуйте актуальний файл та задайте `META_PRIORS_FILE`). Не перезапускайте виконавця без перевірки стану заявок. VPS і живе OKX підключення в рамках цієї роботи не запускалися.
