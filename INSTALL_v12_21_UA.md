# BZU v12.21.0 — зміни за чеклістом

Версія запуску та ядра: `full-ict-v12.21.0-bzu-checklist`.
Архів містить лише змінені та необхідні нові файли. Це готовий код для заміни у вашому репозиторії; завантаження архіву саме по собі не оновлює GitHub і не запускає бота.

## Встановлення

1. Розпакуйте ZIP. Скопіюйте його файли в корінь BZU-Signal-Bot зі збереженням шляхів.
2. Обов'язково замініть `.github/workflows/main.yml`. Файл `WORKFLOW_main.yml` — його ідентична копія для ручного встановлення.
3. Додайте нові `bzu_policy.py` і `test_v12_21_checklist.py`. Замініть також усі інші Python-файли з пакета: оновлення частини залежностей недостатньо.
4. Збережіть свої поточні `last_signal_v6_4.json`, `signal_journal_v6_4.json`, `market_history_v12.json`, `research_market_v12_6.json`. У пакеті немає їхніх замін. Історія, номери ордерів та вже відкриті позиції зберігаються.
5. Наявні GitHub Secrets `TELEGRAM_TOKEN` та `TELEGRAM_CHAT_ID` залишаються потрібними. Після коміту виконайте Actions → BZU Auto Bot → Run workflow для першого звіту.

Розклад — `*/15 * * * *`: один кінцевий запуск кожні 15 хвилин. Звіт захищений від повторів у тому самому 15-хвилинному інтервалі. GitHub може почати запланований запуск із затримкою; точна доставка в секунду :00/:15/:30/:45 не гарантується. Постійного серверного процесу немає.

## Нові правила

| Правило | Реалізація |
|---|---|
| Вхід на випередження | Ліміт від підтвердженої OB/FVG; статус NEW PENDING LIMIT у найближчому 15m звіті |
| Дві частини входу | L1: ближня межа + буфер; L2: середина зони; по 50% робочого обсягу цього сетапу |
| Буфер | LONG: верхня межа + max(0.03, 0.06 × ATR15); SHORT: нижня межа − той самий буфер |
| Швидкий підхід | Свічка >1.8 ATR15 переводить вхід на середину зони замість окремого вето |
| Стоп | Структурний екстремум ±0.25 ATR15; мінімум 0.20, максимум 0.80; спочатку спроба глибшого входу, потім відмова, якщо геометрія все одно не підходить |
| Дальність | До 3.5 ATR15 від поточної ціни; віддалений рівень не підтягується за ціною без нової структури |
| Потенціал | Фінальна структурна ціль від 1.8R; пріоритет цілей 2.2–3R; дальня ціль не вигадується |
| TP1 | 1R від фактичного середнього входу; закриття 60% фактично набраного обсягу |
| Решта після TP1 | Невиконаний L2 скасовується; SL решти переноситься на середній вхід ±0.02 з наступної спостережуваної хвилини |
| TP2 | Закриває решту 40%; якщо L2 набрався до TP1, середній вхід і TP1 перераховуються |
| Catch-up | Новий вхід за поточною ASK/BID лише після перевіреного дотику за останні 15 хв, руху до 0.25R та цілого SL |
| Запізнілий сценарій | WAIT RETEST; минулий дотик ніколи не записується як реально опублікований раніше ордер |
| Перший тест | Дотик з подальшим відскоком ≥0.5R позначає зону MITIGATED; окремий реєстр не дозволяє відновити її просто таймером |
| Скасування | TP1 до входу, TTL 120 хв, закінчення дня о 22:00 за Києвом, підтверджений протилежний BOS/CHoCH |
| Напрямок | Один ринковий режим; за трендом лише відповідна сторона; у боковику — край після зняття ліквідності, середина 30–70% заборонена |
| Зустрічний сценарій | OPEN зберігає напрямок; протилежний PENDING потребує структурного зламу та підтвердженого скасування старого ліміту |
| Портфель | До двох зон одного напрямку; кожна може мати два ліміти. Це максимум чотири частини заявок, а не чотири незалежні позиції |
| Відкрита позиція | Нові зони не додаються; вже опубліковані дозволені частини та зони супроводжуються |
| Близькі зони | Злиття на відстані <0.5 ATR15; спільний дальший SL, повторна перевірка геометрії; якщо злиття непридатне — залишається найкращий придатний початковий план |

Новий чекліст замінює попередні правила стопа 1%, TP1 2%, виходу всім обсягом та заборони часткових фіксацій **для нових планів**. Старі вже відкриті плани завершують свій збережений контракт без переписування минулих результатів. TTL та 22:00 скасовують невиконані ліміти; самі по собі вони не закривають OPEN до TP1. Нові OPEN закриваються за SL/TP, а не просто таймером.

Інтервал 0.15–1.20 до рівня використовується як орієнтир завчасного планування. Додаткового статичного блокування лише за цим інтервалом немає: гранична дальність визначається 3.5 ATR15. За запуску раз на 15 хв нова зона публікується на найближчому запуску, а не в момент кожного закриття 1m/3m.

## Бали замість каскаду вето

| Підтвердження | Бали |
|---|---:|
| Свіжа OB/FVG | 40 |
| Зняття ліквідності свінгу / сесії | 20 |
| Узгодження HTF | 15 |
| Активна сесія та нормальний підхід | 15 |
| Позитивне підтвердження meta / edge | 10 |

Поріг — 55. A+: 75–100; B: 55–74 із рекомендацією 0.5 робочого обсягу. Підтверджений sweep сесійного рівня з подальшим 15m MSS отримує пріоритет A+. Внески різних джерел у придатному кластері підсумовуються до 100.

Meta, edge, adverse-selection та прогноз не мають індивідуального права заборонити новий придатний план. Поріг 55 не обходить обов'язкові перевірки: підтвердження ICT, актуальність зони, коректні дані, режим, геометрію, час життя та місткість портфеля. Дві зайняті зони не перетворюються на третю через високий бал. Бали — не ймовірність виграшу.

Оригінальні 24 детектори збережені. Кожен виконується на 15m/1H/4H, а іменні ICT-контракти залишаються обов'язковими. Незалежні BOS/FVG та сесійні сценарії мають окреме походження, без видавання їх за спрацювання іншого детектора.

## Дані, виконання та статистика

Кожний запуск завантажує до 300 хвилинних свічок і добирає історію до попереднього запуску. Для супроводу використовуються послідовні закриті 1m High/Low. Розрив історії зберігає попередній checkpoint і зупиняє нові рішення. Незакрита хвилина може підтвердити вже пробитий SL, але не створює підтвердження входу або прибутку.

Навіть 1m OHLC не визначає порядок усіх тіків. Якщо в одній хвилині можливі SL і TP, враховується SL. Якщо ліміт опубліковано всередині хвилини, яка торкнулася входу, виконання позначається невизначеним і потребує перевірки; воно не додається до WR. Для архівів без 1m використовується явно позначений грубий 3m прогін, а не вигадані хвилини.

Після TP1 журнал містить реалізовану частину та ознаку успішного TP1. Підсумкова угода отримує один WIN/LOSS після завершення залишку з урахуванням комісій і можливого розриву ціни. TP1 не видається за закриття всієї угоди та не завищує підсумковий WR.

Це бот публікації сигналів і модельного журналу. Він не відправляє автентифіковані торгові заявки біржі й не може сам змінити SL/TP у вашому терміналі. Реальні заявки і захист позиції треба виставляти за сигналом у терміналі; історичне повідомлення не є підтвердженням біржового виконання.

Telegram відправляється до важких архівів, основного state та експорту журналу. Перед доставкою записується компактний файл відновлення `notification_checkpoint_v12.json`, щоб збій після відправки не стер відомості про угоди. За успішного збереження він видаляється; за збою workflow зберігає його разом зі станом.

## Перевірка

```bash
python -m py_compile *.py
python bot_oneshot.py --self-test
python audit_replay_v12_9.py . replay-market.json
python audit_replay_v12_9.py . replay-clean.json --archive research_market_v12_6.json
```

`--self-test` виконує набір чинних контрактів v12.21, включно з потрібними перевірками scan-gap, entry-admission, ранніх лімітів і всіх 24 детекторів. Старі несумісні перевірки доступні окремо: `python bot_oneshot.py --self-test --all-archived-tests`. Вони залишені для порівняння попередніх політик і не є зеленим набором для нового чекліста.

Підсумок фактичних перевірок та обмеження історії наведено у `VALIDATION_v12_21_UA.md`. Заявлений у чеклісті WR 75–85% не вважається доведеним результатом.
