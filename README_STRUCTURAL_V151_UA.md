# BZU MULTI v15.1 STRUCTURAL — оновлення MEXC PAPER

## Встановлення без втрати поточних угод

Рекомендовано використовувати PATCH, а не замінювати весь репозиторій. Перед оновленням збережіть актуальні `multi_scanner_memory.json`, `multi_scanner_state.json` та інші журнали. Не перезаписуйте їх архівними знімками. Дочекайтеся завершення старого запуску Actions і замініть файли патча, включно з `.github/workflows/main.yml`. Залишайте тільки один активний контур запису пам'яті. Запустіть Actions → **BZU MULTI v15.1 — MEXC scanner** → Run workflow. Перевірте кроки scan, persist і deploy-pages, потім зробіть примусове перезавантаження сторінки. Якщо репозиторій публічний, нова сторінка може читати останній знімок гілки без очікування наступного Pages deployment; для приватного репозиторію використовується тільки опублікований знімок. CDN та планувальник GitHub можуть затримувати дані. Немає гарантії оновлення кожні 3 хвилини лише на GitHub Actions.

## Що змінено

- Шість торгових сімейств залишаються, кожне оцінюється для LONG/SHORT. Спочатку перевіряється MARKET за поточною придатною ціною; якщо геометрія або відхід від тригера неприйнятні, перевіряється LIMIT на підтвердженому близькому ретесті. Не штучно зменшуємо SL і не вигадуємо ціль для проходження RR.
- Структурний SL лежить за рівнем інвалідації з ATR-буфером і мінімальною волатильнісною відстанню. Верхній допуск дистанції адаптивний; при надто далекій інвалідації модель залишає WATCH. Позиція перераховується від фактичної початкової дистанції стопа та обмеження плеча.
- TP перед найближчим значущим підтвердженим рівнем ліквідності M15/H1 або розрахункова проєкція, якщо такого рівня в межах бажаного руху немає. Проєкція не є підтвердженим майбутнім рівнем. Недостатня чиста винагорода — WATCH, а не примусово широкий TP.
- Фіксоване переміщення на +0.05R після 0.9R або +0.55R після 1.4R більше не застосовується до нової геометрії. Структурний трейлінг після сприятливого руху від 1.25R потребує трьох повних послідовних M5, відновлених з M1 після входу, підтвердженого свінгу та закриття за його протилежним екстремумом. Новий SL має покривати оцінені комісії/прослизання, залишати ATR-простір до ціни й не збільшувати ризик. Він діє лише після закриття підтверджувальної свічки.
- При міграції відкритих v15.0 позицій початкові entry, initial_stop, stop, TP, R, розмір, час входу та курсор не змінюються. Новий структурний трейлінг починається з часу першого циклу v15.1, а не заднім числом. Старі заявки також не переписуються. Старі записи залишаються в історії, але не навчають метамодель v15.1. Денний показник дашборда агрегує завершені угоди всіх версій за день.
- Пейсинг REST-запитів 0.14 с між початками запитів у процесі; MEXC документує 20 kline / 2 секунди. Один повтор для порожньої або помилкової відповіді. Відсутні старші свічки відновлюються лише з повних послідовних молодших реальних OHLCV; не створюються вигадані свічки. Дані, які залишилися недостатніми, позначаються явно. Відсутність всіх придатних даних не освіжає час останнього успішного аналізу.
- Сканування та Pages deployment мають окремі групи concurrency; черга Pages не тримає блокування запису пам'яті. Свіжі знімки публічного репозиторію доступні через raw GitHub, як додаткове джерело до Pages. JS порівнює `updated_ts` і `last_attempt_ts`; не відкочується на старі знімки та показує джерело, вік, помилки і номер запуску.

## 3 хвилини: постійний worker (рекомендовано)

GitHub Actions мінімум 5 хвилин, можливі затримки. Для циклу 180 секунд потрібний постійно ввімкнений Linux/VPS або Docker-хост. Після перевірки завершення останнього GitHub-циклу встановіть у GitHub Settings → Secrets and variables → Actions → Variables `BZU_SERVER_MODE=WORKER`, щоб вимкнути GitHub-сканер. Не запускайте два незалежні контури одночасно. Скопіюйте останні, а не архівні, `multi_scanner_memory.json` та `multi_scanner_state.json` у `data/` на хості. Якщо журнал справді новий, можна явно встановити `BZU_ALLOW_EMPTY_LEDGER=1` у .env; для наявних угод цього не робіть.

```sh
mkdir -p data
# Скопіюйте актуальні JSON з вашого репозиторію у data/ перед запуском.
docker compose up -d --build
docker compose logs -f bzu-mexc-worker
curl -i http://127.0.0.1:8080/healthz
```

Worker починає цикли приблизно кожні 180 с, не перекриває їх і має граничний час 150 с на дочірній процес. У разі помилки публікує heartbeat з FAILED_CYCLE і залишає попередній час аналізу. `/healthz` повертає 503 при відсутніх/застарілих даних або збої, 200 при свіжому OK/DEGRADED. Docker healthcheck відображає статус; `restart: unless-stopped` перезапускає завершений контейнер, але сам по собі не перезапускає лише unhealthy-контейнер. Для віддаленого доступу налаштуйте HTTPS reverse proxy на хості. Dashboard worker: http://127.0.0.1:8080/ (або адреса вашого проксі), а не стара GitHub Pages URL. Старий Pages URL не стає автоматично дашбордом worker. Не відкривайте порт напряму в інтернет без належної конфігурації доступу.

## Перевірки

```sh
python -m unittest test_mexc_structural_v151 test_mexc_hybrid_v15 test_mexc_multi_scanner
node --check multi_scanner.js
node test_mexc_dashboard_v151.cjs
```

На момент складання: 37/37 Python, 4 перевірки JS. Перевірено синтаксис Python/JS та YAML. Тести моделюють API і свічки; реальна доставка з GitHub, довготривала доступність MEXC і 180-денний бектест не перевірені. Поточний режим PAPER, не виставляє реальні ордери. Статистика враховує оцінені витрати без funding; спільний ліміт маржі двох слотів залишився без змін. Для реальних позицій біржові SL/TP мають існувати незалежно від браузера або бота. Нові параметри не гарантують 60% вінрейту чи прибутку. Відсутність тикової історії не дозволяє точно визначити черговість виконання всередині хвилини.
