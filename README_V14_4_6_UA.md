# BZU v14.4.6 — Adaptive Entry Engine

Патч призначений для останнього наданого архіву v14.4.5 `BZU-Signal-Bot-main(1).zip`.

## Встановлення

1. Зробіть резервну копію репозиторію та розпакуйте патч у його корінь із заміною однойменних файлів. У Git додайте також **приховані** `.github/workflows/main.yml` і `.github/workflows/calibrate_meta_model.yml`.
2. Не видаляйте `last_signal_v6_4.json`, `signal_journal_v6_4.json`, `live_state.json`, `meta_priors.json` або секрети GitHub. Вони навмисно не включені до патча.
3. Зробіть commit. Перевірте GitHub Actions → `BZU Auto Bot — ICT v14.4.6` → Run workflow. На час перевірки використовуйте PAPER, не LIVE. Якщо використовуєте worker, перевірте, що він використовує оновлений код, не запускайте два виконавці одночасно.
4. Оновіть GitHub Pages і браузер (Cmd+Shift+R). UI та сервер повинні показувати v14.4.6 після успішної публікації нового `live_state.json`. Якщо сервер старий, перевірте журнал workflow; не редагуйте збережену версію вручну.
5. GitHub Actions → `BZU Meta Calibration v14.4.6` → Run workflow: days=180, scan_minutes=5 для GitHub або 3 для worker, adaptive_exits=SHADOW якщо такий режим у production, publish=false для першого контрольного прогону. У результаті завантажте artifact `bzu-meta-calibration` і перевірте report.json. Публікуйте лише після успішної незалежної валідації та збігу налаштувань; плановий запуск — неділя 03:17 UTC. Ліміт GitHub Actions на час виконання і доступність OKX можуть потребувати запуску калібрації на власному сервері.

## Логіка

- 24 первинні детектори не видалені; структурні перевірки, SL, мінімальний RR, обмеження ризику та запобігання подвійним позиціям залишені.
- Зі строгого M15-тригера вилучено автоматичний примус лише через назву сетапу/зони або належність до NY. M15 залишається для контртренду, виснаження, пізнього ризикового входу або сильного зустрічного руху. Окремий NY post-sweep контракт збережено.
- EARLY_LIMIT лише для свіжої ще не торканої зони, узгоджених H1/H4, спокійного підходу, пасивної ціни, свіжої котировки та прийнятного спреду; у разі нового зустрічного імпульсу заявка підлягає скасуванню. Немає нового обов'язкового відбою для всіх угод.
- M1/M3/M5 використовують завершені, суміжні свічки; M3/M5 агрегуються з M1 без використання майбутніх даних. M1 вимагає локального зламу, M3/M5 — зламу або відбою. Захист від пізнього входу перевіряє ATR та початковий R.
- Планувальник, фінальний маршрутизатор і UI розпізнають ADAPTIVE_CLOSED_RECLAIM. Існуючі маршрути, які відповідають старим структурним контрактам, збережені; попередні пасивні входи позначаються LEGACY_LIMIT.
- Нова схема `bzu-expectancy-v3-routes` вчить P(win), середній виграш/збиток, P(fill) та EV за окремими маршрутами. Історичні v2 мітки не видаються за нові route labels. Стара сумісна байєсівська модель може залишатися fallback; нова статистика не змінює ризик/ранжування, поки саме цей маршрут не пройшов незалежний holdout. Поточний вибір маршруту правиловий; не стверджується, що EV-оптимізація вибору маршруту вже доведена.
- Shadow Ledger фіксує лише причинно доступні альтернативи з тим самим ідентифікатором зони й окремим маршрутом, без реального розміщення. Порівняння matched_route_comparison рахує тільки епізоди, де обидва маршрути мають завершений результат (незаповнення — 0R); незавершені/цензуровані не використовуються. Корельовані спостереження не додаються як незалежні глобальні голоси.
- Ранній і швидкий маршрут не може виправити затримку GitHub cron сам по собі. Для M1/M3 необхідний безперервний worker/часті спостереження; частота отримання та публікації даних залежить від фактичного запуску. Не змінено розгортання, інтервал GitHub, виконавця біржових заявок, funding або динамічні виходи.

