# BZU v14.4.7 — відновлення швидких входів і калібрації

Патч для BZU v14.4.6 з архіву `BZU-Signal-Bot-main (1)(1).zip`. Режим PAPER рекомендований до незалежної перевірки. Усі 24 сетапи збережено. Старі журнали, конфігурацію Telegram, активні позиції, стан і `meta_priors.json` не замінювати.

## Встановлення

1. Зробіть резервну копію репозиторію. Розпакуйте ZIP у корінь репозиторію з перезаписом файлів, не видаляючи інші файли. Збережіть шляхи: `scripts/run_calibration_segment.sh`, `.github/workflows/main.yml`, `.github/workflows/calibrate_meta_model.yml`. Обидва YAML також надаються окремим архівом без прихованої папки. На Mac Cmd+Shift+. показує приховані файли. Якщо завантажуєте файли через GitHub, створіть зазначені шляхи.
2. Commit. Запустіть BZU Auto Bot — ICT v14.4.7. Перевірте успішність етапів та версію сервера і UI v14.4.7; перезавантажте сторінку через Cmd+Shift+R.
3. У BZU Meta Calibration v14.4.7 виберіть `days=14`, `scan_minutes=5` для GitHub, `adaptive_exits=SHADOW`, `publish=false`, `resume_run_id` порожній. За іншого production режиму змініть scan/exits відповідно до нього. Попередній запуск v14.4.6 може дати звіт для порівняння, але його прогрес не сумісний з v14.4.7. Для нового калібрування потрібен новий запуск.

## Торговий алгоритм

- Закриті тригери M1/M3/M5 шукаються з часу попереднього сканування (не більше 20 хв). Вхід лише за поточною котировкою; старий close не є ціною виконання. Потрібні безперервні M1, чинний reclaim, не пробитий SL і близькість актуальної ціни до зони. Прострочений, неповний або зруйнований сценарій відхиляється. RR, ризик та інші структурні перевірки залишено.
- EARLY LIMIT допускає нейтральний H1, якщо H4 підтримує напрямок і є підтвердження локальної структури/трендового якоря. Свіжість, спокійний підхід, відсутність зустрічного імпульсу, пасивність ціни, spread і наявні ризикові обмеження збережено.
- Контртренд: M5 дозволено за узгодженого H1, сильного мікрозламу, rvol >= 1.2, спрямованого тіла >= 0.65 ATR M5 та без ознак шоку/запізнення/виснаження. Інакше діють попередні захисні умови M15. Незмінні обмеження контртрендового ризику та NY post-sweep. Нова умова перевіряється у фінальному маршрутизаторі, а не лише в планувальнику.
- Дашборд отримує конкретну причину фінального відхилення і дані про підтвердження. Замість універсального M15 показує актуальний серверний код або нейтральне очікування. Реальні умови M15 та структурна аналітика M15 не видалені.
- Нова сигнатура стратегії: старі expectancy prior не використовуються як валідовані v14.4.7. Сумісний старий байєсівський prior може лишатися в режимі transfer. До нової незалежної перевірки статистика маршрутів не повинна самостійно масштабувати ризик.

## Калібратор

Кеш свічок за інструментом, таймфреймом і точним діапазоном; контроль цілісності. Після заморожування вхідних даних replay використовує ті самі свічки при відновленні. Повторні ATR, pivots, M5, VWAP та інші розрахунки кешуються/оптимізовані. Не вимикаються сетапи, не змінюється вибраний інтервал сканування. Прогрес: виконано/заплановано, %, час історичної події, scans/s.

Локальний checkpoint (`calibration/checkpoint.json.gz`) пишеться атомарно кожні 100 сканувань або після 60 с між скануваннями, а також на плановій паузі. GitHub зберігає заморожений датасет і checkpoint в `bzu-calibration-resume-<attempt>-<segment>` після першого сегмента (5 хв реплею) і наступних сегментів (30 хв реплею). До 10 сегментів за запуск. Це бюджет реплею, не обіцянка тривалості job. GitHub runner не зберігає локальні файли після видалення: якщо скасовано до першого успішного upload, відновлення з цього запуску може бути неможливим; якщо скасовано посеред сегмента, можливе повернення до останнього завантаженого checkpoint.

### Відновлення через GitHub

Якщо статус `PAUSED` або запуск перервано і вже є артефакт `bzu-calibration-resume-*`, відкрийте Summary цього запуску. Скопіюйте ID з URL `/actions/runs/<run_id>` (не ID job). У новому Run workflow залиште ті самі days, scan_minutes, adaptive_exits, встановіть `resume_run_id=<run_id>` та `publish=false` для тесту. Скрипт завантажить найбільш просунутий повний checkpoint і frozen history; перевірить сигнатуру стратегії, конфігурацію й SHA256 датасету. Змінений код чи конфігурація потребують нового запуску. Термін збереження checkpoint-артефактів 14 днів (за умови політик репозиторію). Результат `PAUSED` не публікується; `COMPLETE` створює report, labels і prior. Навіть після COMPLETE prior публікується лише за `publish=true` (або плановим workflow) та успішної валідації й незмінної стратегії. Для незалежної діагностики завантажте `bzu-meta-calibration`.

Калібрування вручну (приклад для локального Python, у корені репозиторію):

```bash
python calibrate_meta_model.py --days 14 --scan-minutes 5 --adaptive-exits SHADOW --history-cache .bzu-history-cache --dataset calibration/history.json.gz --checkpoint calibration/checkpoint.json.gz --status calibration/status.json --max-seconds 300 --labels calibration/labels.json
# після PAUSED / переривання, якщо обидва файли збережено:
python calibrate_meta_model.py --days 14 --scan-minutes 5 --adaptive-exits SHADOW --dataset calibration/history.json.gz --checkpoint calibration/checkpoint.json.gz --resume --status calibration/status.json --labels calibration/labels.json
```

## Фактичні перевірки

`VALIDATION_V14_4_7.json` містить повні порівняльні звіти. Архів реальних спостережень OKX 4–5 листопада 2026: 152 сканування, 4 прибуткові портфельні угоди в обох версіях, 4.411641 R net, 2.029858 R з множниками ризику. Міток 19 в обох. Звичайний реплей: 105.35 с -> 50.82 с (2.07x); безперервний реплей та реплей з паузою після 88 сканів і відновленням в окремому Python-процесі дали рівні JSON prior/report/labels. Статус INSUFFICIENT_HOLDOUT. Умови `scan_minutes=15` для цього архіву не означають штучно створені M15-скани: використані збережені фактичні timestamps. Комісії включені згідно з Config.from_env. Вирішальним є незалежний більший тест при production cadence.

Цільові Python-тести: 75/75. Дашборд: 11 перевірок у Node (без справжнього браузера). Старий UI-тест після оновлення очікуваних wait-повідомлень все ще зупиняється на історичному PENDING vs OPEN. YAML, shell та синтаксис модулів перевірено. Hosted GitHub Actions, завантаження повних 14/180 днів OKX і реальне виконання не перевірені в цьому середовищі. Тест не доводить підвищення прибутковості чи кількості угод. Нова логіка входу перевірена також на синтетичних LONG/SHORT сценаріях.
