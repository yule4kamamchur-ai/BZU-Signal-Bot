# BZU v12.23.0 — Master Plan

Патч для прикріпленого архіву BZU-Signal-Bot-main (1)(7).zip.

## Встановлення

1. Розпакуйте ZIP у корінь свого репозиторію та замініть однойменні файли зі збереженням шляхів.
2. Обов’язково замініть `.github/workflows/main.yml`: він містить новий `EXPECTED_BOT_VERSION`. `WORKFLOW_main.yml` — його синхронна копія.
3. Збережіть наявні файли стану та журналу. Їх немає в цьому патчі.
4. Перевірте локально: `python bot_oneshot.py --self-test` — очікується 48 успішних перевірок.
5. Завантажте зміни в GitHub. Розклад залишається `*/15 * * * *`, запуск — `bot_oneshot.py --auto-report`. Ручний Run workflow, як і раніше, викликає `--notify`. GitHub може затримувати початок запланованого запуску; точний час доставки не гарантується самим cron.

## Що реалізовано

| Зміна | Поведінка |
| --- | --- |
| RVOL | Об’єм свічки події / середній об’єм 20 попередніх закритих свічок цього ж TF. Формування зони або sweep із RVOL ≥ 1.35 дає +15 один раз; BOS із RVOL < 0.70 дає −15. |
| Session VWAP | Від 00:00 UTC, HLC3 × об’єм. Повне денне покриття 15m плюс хвилинні дані без подвійного рахунку. Підтверджений LONG на/вище VWAP, SHORT на/нижче отримує пріоритет A+ та +3 до порівняльного ранжування. |
| TP1/TP2 | Перед останнім перетнутим рівнем .00/.50: LONG 75.03 → 74.97; SHORT 73.97 → 74.03. |
| SL | Стоп у межах 0.01 від .00/.50 відсувається назовні щонайменше на 0.05: LONG 74.00 → 73.95, 73.99 → 73.94. Для SHORT симетрично. |
| Impulse Brake | Усередині останньої закритої 15m перевіряються всі три закриті 5m. Після раннього несприятливого імпульсу остання 5m має показати поглинання або пінбар у потрібній зоні та напрямку. |
| 5m без нового запуску | Формується з усіх п’яти підтверджених хвилин кожного інтервалу. Пропуск хвилини не дозволяє підтвердження. Додаткові запити, сервер чи повідомлення між звітами не потрібні. |
| Replay | Враховує наявні закриті 1m/5m, не допускаючи майбутні свічки. |

Підтвердження 5m знімає саме Impulse Brake. Сетап ще має пройти перевірки походження зони, актуальності, SL/TP, напрямку та контракт свого ICT-сетапу. У перевіреному сценарії це дозволяє виставити пасивний ліміт у поточному запуску.

Корекція TP може зменшити його відстань від входу. Після неї заново перевіряються порядок TP1/TP2 та допустимий фінальний R:R. Якщо цілі збіглися, опинилися за входом або потенціал недостатній, новий план відхиляється з окремою причиною. Стоп не стискається назад для штучного проходження перевірки. Якщо TP1 після корекції нижче 1R, перенесення стопа в беззбиток усе одно чекає досягнення 1R.

Старі відкриті та очікувані плани зберігають ціни й умови виходу. Частки виходу, наявні у вихідній v12.22, не змінювалися. Старі навчальні спостереження архівуються окремо від нової політики.

## Перевірки та межі результату

- `python bot_oneshot.py --self-test`: 48/48, з них 31 нова перевірка v12.23.
- Перевірено LONG/SHORT, часову причинність RVOL, UTC VWAP, 5m пінбар/поглинання, пропуски/незакриті дані, корекцію SL/TP, R:R, результат після комісій, збереження старих планів і частоту звітів.
- Перевірено синтаксис Python, YAML, збіг версій launcher/engine/workflow. Файли журналу, стану та формат компактного повідомлення не змінено.
- Повний історичний набір не проходить: вихідний архів — 619 тестів, 406 невдалих перевірок і 5 помилок; після патча — 650 тестів, 402 невдалі перевірки і 3 помилки. Частина тестів описує попередні умови входу, геометрію та старий текст повідомлень. Додаткові 17 невдалих перевірок v12.22 використовують початкову геометрію, яку тепер відхиляє захист R:R. Повні підсумки за модулями є у VALIDATION_v12_23.json.
- `--self-test` перевіряє поточні контракти; весь історичний набір залишається доступним через `--self-test --all-archived-tests`.
- Це перевірка реалізації. Незалежний історичний тест прибутковості та підтвердження win rate не проводилися. Реальний запуск у вашому GitHub цим патчем не виконано.
