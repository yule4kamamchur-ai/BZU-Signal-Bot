# BZU Signal Bot v12.3 — виправлення та встановлення (13.10.2026)

## Що змінилося

1. **15 хвилин — Telegram, 5 хвилин — перевірка ринку.** Планувальник GitHub Actions має два розклади: о 00/15/30/45 хв — звіт у Telegram і торговий цикл; о 05/10/20/25/35/40/50/55 хв — торговий цикл та супровід БЕЗ Telegram. За один 15-хвилинний звіт показує події всіх попередніх перевірок; кожна подія має номер ордера та простий значок.
2. **SL — не менш ніж 0,40% від ціни входу** для будь-якого з 24 сетапів. Додатково враховано 3m ATR та структурну інвалідацію. Якщо досяжна найближча ціль не покриває новий ризик, комісію і модельне прослизання — кандидат *відхиляється*, а не отримує штучну далеку ціль. `ABS_MIN_STOP_PCT` нижче 0.004 є помилкою конфігурації.
3. **TP1/TP2/TP3** залежать від тієї самої остаточної величини ризику, що й стоп; перевіряється `MIN_NET_RR` та частка витрат. Ніяких гарантованих 2R/3R, якщо на графіку немає вільного простору до наступної перешкоди.
4. **Вік anchor і TTL ліміту відокремлені.** Anchor не можна використати після `SETUP_AGE_MINUTES` (типово 180), але *новий* ліміт отримує незалежні `LIMIT_TTL_MINUTES` (типово 120), максимум до завершення внутрішньоденної сесії. Не подовжуються старі вже виставлені плани заднім числом.
5. **TREND_IGNITION** перевіряє пробій діапазону, порахованого без свічки пробою. **FAILED_OPENING_RANGE_BREAKOUT** виправляє сторону buffer інвалідації. **TIME_OF_DAY_ADAPTIVE** використовує завершений фіксований UTC 02:00–07:00 діапазон Азії, а не всю добу.
6. **Тижневі рівні** будуються з історії 1H (типово 220 свічок), не з 50-годинної історії 15m. Якщо історія не досягає початку понеділка — тижневі рівні не підставляються. Opening range вважається завершеним лише за наявності чотирьох відповідних 15m свічок.
7. **Пізнє підтвердження PAPER-сценарію** тепер може оновити навчальний сценарій лише *до його заповнення* і лише на майбутні свічки. Історичне постфактум підтвердження прибутку заборонене.
8. **Dashboard** читає `last_signal_v6_4.json` і `signal_journal_v6_4.json`, бачить обидва місця, стани, тейки, останні події, фактичну кількість перевірених детекторів і застереження щодо непідтверджених 70%.
9. **Наявні відкриті PAPER-плани не переписуються.** Під час переходу v12.2 → v12.3 зберігаються їхні вхід, SL, TP, старий TTL. Нові правила геометрії застосовуються лише до нових пропозицій.

## Встановлення в GitHub

1. Зробіть backup обох файлів зі свого репозиторію: `last_signal_v6_4.json` і `signal_journal_v6_4.json` **у їхній останній живій версії**.
2. У тому самому репозиторії **оновіть файли з ZIP поверх наявного коду**: `bot_oneshot.py`, `full_limit_engine.py`, `signal_quality.py`, `research_validate.py`, `index.html`, `.github/workflows/main.yml`, `setup_preservation_manifest.json`, `test_*.py`. Не видаляйте файли стану й журналу та не завантажуйте їхні старі копії з архіву від 13.10.
3. Збережіть у GitHub Secrets `TELEGRAM_TOKEN` і `TELEGRAM_CHAT_ID`; переконайтеся, що GitHub Actions мають право записувати в репозиторій (Workflow permissions: Read and write permissions), а заплановані завдання увімкнені.
4. На вкладці **Actions** один раз запустіть **Run workflow** вручну. У журналi повинні бути `--self-test`, `--legacy-self-test`, один 15-хвилинний звіт і збереження стану.
5. Перевірте, що у розкладі `*/15 * * * *` Telegram отримує звіт, а проміжні GitHub запуски `5,10,20,25,35,40,50,55` Telegram **не** надсилають. Стан має оновлюватися на обох типах запусків.
6. Не змінюйте вручну `LIMIT_TTL_MINUTES` і комісії, коли є відкритий новий v12.3 план: для зміни торгової конфігурації дочекайтеся закриття активних місць.

## Межі та ризики

- **70% win rate НЕ підтверджено.** У наданому стані 5 завершених PAPER-угод, з яких 2 прибуткові: **40%**, або для двох виконаних угод після оновлення v12.2 — **1/2 = 50%**. Із 25 навчальних результатів лише деякі відповідали контекстному відбору — це не статистична гарантія 70%.
- Системі треба накопичити достатньо *незалежних* спостережень і перевірити її на відкладеному, не використаному для підбору даних періоді. Піднімати win rate фільтрами на цих 5 угодах — переоптимізація.
- Усе ще **PAPER**, не справжні заявки на біржі. 3m OHLC показує інтервал, а не точну секунду виконання, тому результат треба вважати модельним.
- GitHub Actions `schedule` може стартувати із затримкою або не запуститися; рівно кожні 15 хвилин чи вхід без жодної затримки на цій платформі гарантувати неможливо. Для точного часу потрібен постійно працюючий сервер і стрім ринкових даних.
- 5-хвилинні запуски збільшують витрату GitHub Actions хвилин та кількість git-комітів; перевірте ліміти свого репозиторію.

## Команди перевірки

```bash
python -m py_compile bot_oneshot.py full_limit_engine.py signal_quality.py test_v12_3_fixes.py
python bot_oneshot.py --self-test
python bot_oneshot.py --legacy-self-test
```

Архів виправлень навмисно **не містить застарілих JSON-файлів поточного стану**. Оновлюйте існуючий репозиторій, а не створюйте порожній стан замість нього.
